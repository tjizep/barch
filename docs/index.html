User / Architecture

BARCH Architecture Overview

BARCH is a low-memory, ordered, sharded cache built on an adaptive radix trie (ART). Two access surfaces: the RESP wire interface (redis/valkey protocol, default port 14000) and the SWIG-generated embedded interface for Python and LuaJIT, which runs against the in-process L1 store.

Tier model

The embedded (SWIG) interface is the L1 fast path: calls resolve in-process against sharded tries. The RESP interface serves the same store over the wire and is also the L2 replication endpoint.

Storage engine

Each keyspace is partitioned into shards. The default store is an ordered ART with adaptive interior nodes (node4, node16, node48, node256) and compressed paths. Set ordered_keys to false to use an unordered hash instead. Consequences that hold for every API:

PropertyGuarantee
Point operationsO(k) where k is key length in bytes — independent of key count n.
Ordered navigationMIN, MAX, LB/FIRST, UB/NEXT descend one root-to-leaf path: O(k), effectively constant time. Needs the ART (ordered_keys default). The unordered hash has no key order.
Range scansO(k + m) for m results; iteration never blocks other readers. On a range-sharded space, cross-shard ranges walk shards in key order and stop early — see Ordered Range Sharding.
MemoryRoughly half of an equivalent hash map. Shared key prefixes are stored once (see Memory & Prefix Elimination). Interior nodes grow adaptively. Values may be compressed (zstd/fsst) inside a VMM-paged arena with defragmentation and LRU/LFU/TTL eviction.
ConcurrencyReader/writer locks per shard. Reads are concurrent and scale linearly with core count; a write serializes only against its own shard.
Ordering is byte-lexicographic with a numeric class below text. MIN/MAX and range endpoints compare numbers as less than strings. Design composite keys (e.g. Morton/Z-order codes) with this collation in mind.

Access surfaces

Two production access surfaces. Call them from the Quickstart and the command index. How they are bound is under Developer.

  • RESP — every command listed here is reachable on the built-in RESP port with its bare name, and on a hosting valkey server with the B. prefix. Signatures identical to valkey/redis behave identically.
  • SWIG — module functions plus Caller, KeyValue, HashSet, OrderedSet, List, and the Value variant type.

Both surfaces address the same named key spaces. The valkey module loader, JNI bindings, and internal C++ headers are out of scope.

User / Quickstart

Quickstart

Two ways in: attach to a running RESP endpoint, or embed the L1 store in your own process via the SWIG module.

1 · RESP endpoint

Any RESP client works. When barch runs as a valkey module, prefix commands with B. on the valkey port; the native barch port (default 14000) takes bare names.

# standalone: valkey hosts the module, barch also listens natively
valkey-server valkey.conf --loadmodule ./build/_barch.so
valkey-cli -p 6379 B.SET greeting hello
valkey-cli -p 14000 GET greeting        # same store, bare names

2 · Embedded L1 (SWIG)

# python
import barch
k = barch.KeyValue()
k.set("hello", "world")
print(k.get("hello"))

# optionally expose the embedded store on RESP so redis-cli can reach it
barch.start("127.0.0.1", 14000)

Unix domain sockets are supported for zero-TCP local serving: barch.start("/tmp/lbarch", 0), then connect with barch.KeyValue("/tmp/lbarch", 0) from another process.

Environment configuration. The Python and Lua modules apply environment-derived configuration at import time, before any user code runs. An explicit setConfiguration() call still wins.

Build from source

sudo apt install build-essential cmake swig python3-dev libssl-dev
cmake -B build -DTEST_OD=ON
cmake --build build --target barch --parallel "$(nproc)"     # SWIG python module
cmake --build build --target lbarch --parallel "$(nproc)"    # valkey runtime
sudo cmake --install build --component barchlua               # luajit → /var/lib/lua/5.1/barch.so
Give --parallel a number. With no number it reaches make as a bare -j, which starts every source at once — around sixty compiles of up to a gigabyte each. A machine without that much memory has the build killed with nothing from the compiler to explain it. Ninja picks its own limit, so this only affects the Makefile generator.
Platform constraint. Linux only, gcc 11+ (any C++20 compiler), amd64+SSE or arm+NEON. Valkey 8.0+ is required only for the module deployment — the embedded and native-RESP paths run without it.

A foreign DSN is a secret. Put it in file:/path or env:VAR. Do not put a database password in the configuration space: that space replicates under PUBLISH, and ACL does not hide those keys from a client that can read it. The server never logs the resolved DSN.
Foreign fill is not PULL. <name>.foreign asks MySQL, Postgres, or Luau on a local miss. It does not subscribe to another barch. PULL is still the unfinished remote-barch path. See Coalesced Foreign Sources for how to configure a query so a GET waits on one shared load.
Eviction and OOM behaviour are configuration-coupled. With no eviction policy and max_memory_bytes reached, inserts throw not enough memory and increment oom_avoided_inserts. The RESP session and the valkey caller turn that into an error reply. See Error Model.
ordered_keys picks the default store. true (the default) keeps keys in the ordered ART, so MIN, MAX, LB, UB, RANGE and COUNT work. false keeps them in an unordered hash instead. Error Model

Failures surface as RESP error replies on the wire and as exceptions or sentinel values in SWIG. The HTTP column is for proxies and SDKs: 429, 409, and 503 are gateway mappings, not wire codes.

BARCH itself never emits HTTP status codes. The mapping column is guidance for proxies and SDK authors, not a description of the wire protocol.

409-class outcomes are data, not faults. A failed NX write and an ADD against an existing key return nil/zero by design. Gateways must translate on reply shape. Matching on RESP error strings alone will miss every conflict.
503-class outcomes are errors at the call site. An over-ceiling insert without an eviction policy raises not enough memory. Alert on that reply and on oom_avoided_inserts (see Statistics).

Retry discipline

  • Idempotent by construction: SET, HSET, ZADD (same member/score), DEL/REM, all reads — retry freely.
  • Not idempotent: INCR/DECR/HINCRBY/ZINCRBY, APPEND, LPUSH, LPOP — retry only when the failure provably occurred before dispatch.
  • Blocking pops (BLPOP/BRPOP) return nil on timeout; treat nil as normal control flow, not an error.
Developer / RESP

RESP Wire Interface

The RESP interface is the L2 access path and the replication substrate. It speaks the redis serialization protocol, so redis-cli, redis-py, go-redis, and redis-rs connect unmodified. A key space prefix on argument zero selects a space for that command alone.

L2 · wireRESP2per-shard RW locks
Design context

Execution model

A native RESP listener binds bind_interface:listen_port. That is port 14000 in the standard deployment, or a unix domain socket when the interface is a filesystem path and the port is 0. Under the valkey module, the same command set is also exported on the valkey port under the B. prefix.

  • Complexity: command dispatch is a hash lookup into the shared function map; the command then runs at the engine complexities on the overview: O(k) point ops, O(k+m) scans.
  • Concurrency: a command acquires the read or write lock of exactly the shards its keys hash (or range-route) to. KEYS and VALUES share a dedicated worker pool (iteration_worker_count), so GET, SET and other low-latency commands keep running. Only another KEYS or VALUES waits.
  • Memory: each connection owns an RPC buffer capped at rpc_max_buffer bytes. A reply that exceeds it fails the call. The buffer does not grow.
Name equivalence. B.GET on the valkey port, GET on port 14000, and KeyValue.get() in SWIG execute the same function against the same shards.

Design context

Key space prefixed commands

Commands stay ordinary RESP arrays. The native listener splits argument zero, the command name, on a colon and treats the part before it as a key space selector for that command only.

# three commands, three spaces, one round trip, no session state changed
catalog:SET sku:00001 widget
sessions:GET tok:9f2
metrics:INCR page_views

Without it, the same work costs six commands and leaves the connection pointing somewhere the next caller did not choose:

USE catalog
SET sku:00001 widget
USE sessions
GET tok:9f2
USE metrics
INCR page_views                # connection is now on `metrics`

Resolution rules

  • Split point is the last colon in the command name. Everything before it is the space name, everything after is the command. A name with no colon, or one ending in a colon, is dispatched unchanged as an ordinary command.
  • Scope is exactly one command. The session's current space is saved before the call and restored after it, so a prefixed command never leaks its selection into the next command on that connection — including on the error path.
  • Selection is skipped when it would be a no-op. If the prefix already names the connection's current space, no switch and no restore occurs; the prefix costs a string compare.
  • The space is created if it does not exist, exactly as USE would, reading its <name>.* options from the configuration space on first reference. See Named Key Spaces.
  • Dispatch and ACL apply to the stripped name. The command is looked up, authorized against its categories, counted, and replicated as if it had been sent unprefixed — catalog:SET is a write+keys command, not an unknown one.
  • Each element of a pipelined batch resolves independently, and the resolved space is carried with the call, so the shorthand is safe to mix freely inside a pipeline including with asynchronous commands.
Connection pools. USE stores the space on the connection. A pooled client shares that connection, so a caller that forgets to re-select runs against whatever space the previous borrower left. The prefix puts the space on the command, so a pool can mix spaces without leaking selection.
Native RESP listener only. The shorthand is implemented in the barch RESP session, so it works on the native port (default 14000) and on unix domain sockets. Commands dispatched through a hosting valkey server resolve against valkey's own command table, where catalog:B.SET is simply an unknown command — use B.USE there.
Command names cannot contain a colon; space names must not. The split is on the last colon, so a:b:SET parses as space a:b, fails the [0-9A-Za-z_]+ name rule, and returns an error. It does not fall back to unprefixed dispatch. The split applies only to argument zero. Colons inside keys are untouched, so catalog:SET sku:00001 widget is unambiguous.

Error tree

  • Prefix failing the name pattern → -ERR from key space validation → 400.
  • Stripped name not in the function map → -ERR unknown command → 400. A malformed prefix does not silently degrade to unprefixed dispatch.
  • Caller lacking the stripped command's ACL categories → -ERR not authorized → 403-class. The prefix grants nothing; see AUTH & ACL.
  • Any exception during resolution is written as an error reply, and the connection's previous space is still restored.

Developer / SWIG Python

SWIG · Python L1 Interface

The barch Python module embeds the full store in-process. Reads resolve in sub-microsecond time because no serialization, syscall, or network hop occurs on the L1 path. The same module can serve its store over RESP (start) and replicate to peers (publish/pull).

L1 · embeddedPython ≥ 3.10per-object mutex + shard RW locks
Design context

Binding architecture

  • Generation: classes are SWIG-generated from src/swig_api.h via src/barch.i. std::vector<std::string> maps to Python lists of str; std::vector<Value> maps to lists of Value.
  • Complexity: identical to the engine — O(k) point ops, O(k+m) ranges — plus a fixed per-call SWIG marshalling cost. No GIL-visible blocking on the fast path; long scans release into worker threads.
  • Memory: data lives in barch's own arenas, outside the Python heap; barch.stats().heap_bytes_allocated is authoritative, not sys.getsizeof.
  • Locking: every handle (KeyValue, HashSet, …) derives from Caller and holds an internal mutex — a single handle is thread-safe but serializes its callers. For parallel throughput, construct one handle per thread; shard RW locks then govern actual contention.
  • Init-time configuration: the module applies environment configuration inside SWIG module init, before user code; explicit setConfiguration() overrides it.
One handle per thread. Sharing a single KeyValue across a thread pool caps throughput at one in-flight call. The engine's linear read scaling is only observable with per-thread handles.

Design context

Sizes, refusals and deliberate differences

How large a key or a value may be

A key and its value live together in one leaf, and a leaf has to fit inside a page. That is a single budget of maximum_allocation_size - 261,888 bytes on the default page size - shared between the two, so a large key leaves less room for the value and the other way round. A pair that does not fit is refused with string exceeds maximum allowed size; it is not truncated and not partially written.

WhatLargest acceptedSharing the budget with
value, with a one byte key261,885 bytesthe key
key, with a one byte value261,885 bytesthe value
hash field name261,880 bytesthe hash name and the field's value
hash field value261,879 bytesthe hash name and the field name
list element261,865 bytesthe list name and the element's index
ordered set member130,924 bytessee below - a member costs twice its length

An ordered set member is the odd one, at roughly half of everything else. A member is stored twice: once in the score ordered key, and once in the member index, whose value is the score key it points at - and that score key contains the member again. So a member is charged about twice its own length against a single leaf's budget.

Until recently these were silent. The insert has always refused an oversized pair, but the write commands did not look at the answer: SET replied OK, SETNX replied 1, and RPUSH replied with a length that LLEN then agreed with - and none of them had stored anything. Every writer reports it now. If you are running a build from before this, a large value may have been accepted and lost.

What a key may contain

  • A key may not be empty, and may not contain a null byte anywhere but at its end. Both are refused. They are not trimmed.
  • A key containing the separator - a space, by default - is stored as several components. It is still one key and behaves as one, but it is encoded differently from a key without one.

Replies are built in memory

Most replies are assembled in memory before they are sent. Redis streams as it goes. That usually does not matter; it shows up wherever a caller can ask for an unbounded amount in one command. KEYS is the exception: matching keys are written to the client as they are found. A negative count to HRANDFIELD or ZRANDMEMBER asks for that many entries with repeats, so it is capped at a million. Beyond that the reply is value is out of range. LCS is bounded differently: its table is the product of the two value lengths in 32 bit cells. Check those lengths before running it on large values.

Deliberate differences from redis

  • DBSIZE counts stored keys. A hash with twenty fields adds twenty. KEYS and SCAN count key names, so the two numbers will not match.
  • There is no set type, so SADD and the S* commands do not exist. Anything a redis test sets up with a set has no equivalent here.
  • An expiry is held as a unix time and survives a restart, but it is measured against the system clock, not a monotonic one. A large correction - an NTP step, or the clock being set by hand - moves every deadline relative to now, and keys expire early or late by however far it moved. redis behaves the same way for the same reason.

Between versions

A shard file records the storage format it was written with. A server refuses a file whose format it does not recognise. The format has changed several times, so a file from an older build will not load. EXPORT writes the data as the commands that would rebuild it - SET, HSET, RPUSH, ZADD - and IMPORT replays them. Run that with the build that can still read the data.

Key/Value & Ordered Operations

Point reads and writes, counters, TTL, glob scans, and the ordered-navigation primitives (MIN/MAX/LB/UB/RANGE/COUNT).

L1 · KeyValue classL2 · RESPpoint O(k)range O(k+m)write: 1 shard W-lock
Design context

Engine implications

  • Point ops (SET/GET/ADD/REM/EXISTS/TTL/EXPIRE/APPEND/counters): one trie descent, O(k) in key length; the key hashes to exactly one shard, so a write takes exactly one shard write lock.
  • Ordered navigation (MIN, MAX, LB/FIRST, UB/NEXT): a single root-to-boundary descent, O(k), independent of key count. Requires an ordered keyspace.
  • Ranges (RANGE K1 K2 count, COUNT K1 K2): seek to K1 then in-order walk — O(k + m). Under hash sharding, a range fans out to every shard, collects up to limit × shard_count candidates, and merge-sorts. With <space>.range_sharded enabled (ordered-sharding branch), the walk starts at the shard owning K1, streams results in key order, and stops at the first key ≥ K2 — nothing collected, nothing sorted; MIN/MAX/LB/UB/COUNT likewise stop at the first shard that can answer. See Ordered Range Sharding. The same walk is the n-gram lookup and the H3 lookup — see N-gram Text Index and H3 Geospatial Index.
  • Scans (KEYS, VALUES with glob): run on a dedicated worker pool (iteration_worker_count). Memory use is capped: a walk that would cross max_memory_bytes just stops. KEYS writes each match to the client as it is found. GET, SET and other commands keep running; only another KEYS or VALUES waits. Unlike Redis KEYS, this is safe to use on a live server. KEYS is not classified dangerous in the ACL model.
  • Allocation: a SET replacing a value reuses or replaces one leaf (leaf_nodes_replaced counts these); inserts may grow one interior node along the path (node4→16→48→256). APPEND/PREPEND reallocate the value in the arena.
Lock constraint. Counters (INCR/DECR) are atomic read-modify-write under one shard write lock. They serialize with all writes to that shard — hot counters on a low shard count are the primary write-contention scenario.

Reference / N-gram Text Index

N-gram Text Index

There is no n-gram command. A sliding window over text is ordinary composite keys in a keyspace you name — usually txt. The gram is the first component; the window offset is a number after a |, so the parser encodes it as an integer. The gram keeps its spaces.

L1L2 · RESPcomposite SET + RANGEoffset is a number
Design context

Gram, pipe, offset

Set txt.key_split to | before the first USE txt. A frame is then one argument: the gram, a pipe, then the offset. The offset token is a number (0, 1, 2…), so it is encoded with the same (base 128)+1 integer order every numeric key already uses. Shared gram prefixes live once in the trie.

A space inside the window is just text. Do not rewrite it as _.

For This is a doc. This is a dog:

USE configuration
SET txt.key_split |
SAVE
txt:SET "This |0"
txt:SET "his i|1"
txt:SET "is is|2"
txt:SET "s is |3"

Put the frames in txt and the source document in another space. RANGE "is is|0" "is is|999999" then sees every offset of that gram, because the number sits after the pipe.

The pipe is the composite separator. It is not a type tag and not a lead byte. The parser sees 0, 1, 2 as integers because they are the token after that |. Unset key_split, a space still splits the key and a gram cannot contain one.
Delete the frames when the source goes. REM of the document does not know about the index. Drop each <gram>|<offset> key you wrote for it, or the next range still names a frame whose source is gone.

H3 Geospatial Index

There is no geo command. A point is an ordinary composite key in a keyspace you name — usually spatial_data. The Uber H3 cell is the first component, as a decimal integer; a unique id sits after a space, so the parser encodes the cell as a number and nearby cells sit nearby in the trie.

L1L2 · RESPcomposite SET + RANGEH3 cell is a number
Design context

Cell, space, id

SET splits a key on spaces. A point is therefore one argument: the H3 cell as a decimal integer, a space, then an id (a name, or a counter). The cell token is a number, so as_composite encodes it with the same (base 128)+1 integer order every numeric key already uses. That is what makes a parent cell's children one RANGE.

examples/flask/geo.py writes {int(h3_index, 16)} {name} at resolution 12. examples/flask/overture.py writes the same shape as {h3_index} {counter} when it loads Overture addresses. Both keep the space ordered.

Those two integers are contiguous in H3's child order, so they are one numeric range. geo.py builds them with h3.child_pos_to_cell and calls:

The second component 0 … 99999999999999 covers every id under those cells.

The space is the composite separator. It is not a type tag. The parser sees the H3 cell as an integer because it is the token before that space. Keep the space ordered (spatial_data.ordered) so numeric order is the trie order.
Delete the composite key when the point goes. REM of a document in another space does not know about this index.

Reference / Ordered Range Sharding

Ordered Range Sharding

Route keys to shards by the range they fall in, not by hash. Shard order then agrees with key order, so a cross-shard ordered read (RANGE, MIN, MAX, LB, UB, COUNT) walks shards in key order and stops early instead of fanning out and merging. A maintenance-thread rebalancer keeps the partition even as data changes.

L1L2 · RESProute: binary search, O(log shards)opt-in per keyspace, off by defaultrebalance: adjacent shard W-lock pairs
Branch status. This page documents the implementation on the ordered-sharding branch (v0.5.8b). On main, <space>.range_sharded is accepted and reported by getRangeSharded() but selects nothing.
Design context

Routing model

The range index

  • Structure: the routing table is a flat sorted vector holding the minimum key of every shard above 0 — at most shard_count − 1 entries. A route is a binary search for the last boundary not above the key; a key below every boundary belongs to shard 0, whose span is open at the bottom. Cost: one atomic load plus O(log shards) over a couple of cache lines, per operation.
  • Lock-free reads: the table is replaced, never mutated — a rebalance builds a new table and swaps it behind an atomic shared_ptr. Routers never lock to read and never observe a half-written table.
  • Never persisted: the table is a function of the shards (each shard's first key), so a load rebuilds it. There is no index file to version or find out of step with the data.

Routing under a moving partition

Unlike hash routing, a key's shard can change while the space is running, so there is a gap between routing a key and holding the lock that stops the boundary moving. Two rules close it:

  • a rebalance changes the table only while holding write locks on every shard whose span is changing — both neighbours, taken in shard order, the new table published before either lock drops;
  • a router routes, takes its lock, then routes again. The same answer proves the key cannot move while the lock is held (moving it needs that lock); a different answer means the boundary moved in between — drop and retry.

The retry cannot spin: losing twice requires two rebalances of the same boundary, which are bounded by the maintenance interval.

Rebalancing

  • Placement: the sweep runs on the keyspace's maintenance thread — never on the insert path — making that thread the sole writer of the table.
  • Algorithm: shards shed to neighbours in both directions, cascading with a per-level budget, shedding only far enough to meet the neighbour halfway. Work per sweep converges on the observed skew (capped on lock pairs, not on passes), which keeps balance even as sweeps get further apart.
  • Tolerance is a band, not a ceiling: the sweep finishes when no shard is above tolerance × average and none is below average ÷ tolerance. The lower bound is what prevents "balanced" partitions with empty tail shards. Measured targets: ≈1.25× peak-to-average, zero empty shards; e.g. 20 000 ascending keys settle across 8 shards at ≤ 1.30×.
  • Moves are not user traffic: a moved key carries expiry, volatile, and compression state across, and op counters are corrected — a rebalance does not appear as inserts and deletes nobody issued. range_shard_keys_moved counts moves instead.

Ordered reads

  • RANGE starts at the shard owning the lower bound, walks shards in order, streams each key as found, and stops at the first key not below the upper bound — nothing is collected, nothing is sorted. Previously the store walked every shard, gathered up to limit × shard_count candidates, and sorted them.
  • MIN, MAX, LB, UB, and COUNT stop at the first shard that can answer instead of reducing over all of them.
  • These fast paths are active only when the shards are a true ordered partition — a space with a pull replication source is excluded even when range-sharded, since keys it answers for may live upstream.
Write-amplification constraint. An append-only (monotonically ascending) workload costs O(shard_count) key moves per insert: every new key lands in the top shard and must cascade down to keep the partition even. Range sharding is opt-in per keyspace and off by default for that reason. Random-order keys barely exercise the rebalancer. Use hash sharding for append-heavy spaces unless ordered cross-shard reads dominate the workload.
Rebalance never touches a pull-fed shard. A shard with pull sources leaves tombstones on delete and may answer for upstream keys, so neither its size nor its minimum means what the algorithm needs. Replicated-into spaces keep hash-style behaviour regardless of the option.

Hash → range conversion

Enabling the option on a space that already holds hash-sharded data triggers a repartition at load: boundaries are chosen from a sample (≤ 4096 keys per shard, sorted, cut into quantiles), then each shard is drained in byte-bounded batches into the new partition. Measured: 5 000 keys over 4 shards convert in ~7 ms, moving 3 696.

Error tree

  • range_sharded on an unordered space → downgraded to hash sharding at space construction.   • INFO SHARD #n with n ≥ shards → shard number out of range.
  • Shard sizes summed from per-shard INFO SHARD calls while a sweep runs may not add up — a key moved between two reads is counted twice or not at all. Not an error; totals settle when the sweep has nothing left to do.
  • Route retry exhaustion cannot occur under the published protocol; a transport-level failure on a routed shard surfaces per the routing error tree.

HashSet H*

Field/value maps under a single key with per-field TTL — the redis hash API plus field-level expiry (HEXPIRE, HEXPIREAT, HTTL, HEXPIRETIME).

L1 · HashSet classL2 · RESPfield op O(kkey+kfield)write: 1 shard W-lock
Design context

Engine implications

  • Layout: fields are addressed as composite paths beneath the hash key, so a field operation costs one descent over key + field bytes; HGETALL/HKEYS walk the key's subtree in O(k + f) for f fields, in field order.
  • Sharding: the whole hash lives on the shard of its top-level key — a multi-field HSET or HMGET touches exactly one shard lock, making it the cheapest multi-value write in the system.
  • Per-field TTL stores an expiry alongside each leaf; expired fields are reaped lazily and by the maintenance cycle, so HLEN may transiently include expired fields.
  • Memory: many small fields share a prefix, so interior-node cost is amortized.
Skew constraint. A single giant hash is one shard's problem: all its writes serialize on one write lock, and reads of that shard contend with them. Distribute hot aggregates across multiple keys when write rates are high.

Replication & Routing

RESP serving (START/STOP), write streaming (PUBLISH/PULL), snapshot block-load (LOAD/RETRIEVE), and per-shard remote routing (ADDROUTE/ROUTE/REMROUTE).

L1 initiatesL2 receivesasync fan-outmulti-writer, last-write-wins
Design context

Topology model

  • Push replication (publish): local writes are queued (out_queue_size) and streamed to the peer's RESP endpoint asynchronously. The local write path never waits on the network — a dead peer degrades to counter drift (attempted_routes vs routes_succeeded), never to write latency.
  • Pull replication (pull): the inverse subscription; two nodes publishing to each other form the multi-writer pair shown below.
  • Foreign fill is not PULL. A space with <name>.foreign set to mysql, postgres, or luau asks that source on a local miss. It does not subscribe to another barch and it does not implement PULL. See Coalesced Foreign Sources.
  • Block load (load(host, port) / RETRIEVE): a bulk snapshot transfer that warms a cold embedded node against a standalone server. Faster than replaying a write stream.
  • Shard routing (setRoute): pins a shard index to a remote host; operations on keys owned by a routed shard execute remotely. This is horizontal partitioning at shard granularity, orthogonal to replication.
  • Memory: the outbound queue is the main replication allocation; it grows with peer lag and is bounded operationally by monitoring out_queue_size.
Consistency contract. Multi-writer replication is asynchronous and convergent, not transactional: concurrent writes to the same key on two publishers resolve last-write-wins on arrival order. Do not place invariants requiring read-your-peer's-write on this path — route the key instead.

Reference / Named Key Spaces

Named Key Spaces

A key space is an independently sharded, independently configured, independently persisted store inside one BARCH process. Spaces are selected per connection (USE) or per handle (KeyValue("name")), can be layered so one resolves misses in another (KSPACE DEPENDS), and can be merged, dropped, or unloaded at runtime.

L1 · handle constructorL2 · USE / KSPACEper-space shard countspace-level shared/unique lock
Design context

Model

What a space owns

  • Its own shards. Shard count is per space (<name>.shards), so a small hot space and a large cold one do not share a lock domain or a partitioning decision.
  • Its own ordering and routing options — <name>.ordered, <name>.range_sharded — plus per-space eviction options set through KSPACE OPTION SET. Unset .ordered inherits the global ordered_keys default (the ART). Set it to 0 to keep that space on the unordered hash.
  • Its own persistence and maintenance thread. Each space starts maintenance on construction; saves, defrag, and (where enabled) range rebalancing are per space.

Naming and reserved names

  • Names must match [0-9A-Za-z_]+. A non-matching name raises. It is not coerced.
  • Internally a user name is suffixed so user spaces cannot collide with system stores. The empty name (and "0") selects the default space, stored internally as node.
  • configuration is a real, replicated space used to carry per-space options; it and the default space are not themselves configurable through those options and are always single-shard in the configuration case.

Construction and caching

A space is built on first reference and cached for the life of the process. Construction is when it reads <name>.shards, <name>.ordered, <name>.range_sharded, and the <name>.foreign* keys out of the configuration space, loads its shards in parallel, and (if range sharded) builds its routing index. Memory allocated during that build is attributed to startup memory. A foreign source is stored on the space. A miss fills from that source; a source miss is an empty tomb, so GET, EXISTS, MGET and TTL treat it as absent and do not ask again. See Coalesced Foreign Sources.

Options are read once, at first reference. Writing <name>.shards or <name>.range_sharded after a handle to that space exists in the process has no effect until restart. Provision the configuration space before constructing the first handle, and re-provision in every process that opens the space. The configuration space is not carried between processes. An unset option falls back to the server default, not to whatever the data was written with.
range_sharded without ordered leaves the space hash routed. The server logs an error. getRangeSharded() reports what the space is actually doing.

Dependent spaces (layering)

  • KSPACE DEPENDS dependent FROM source makes dependent resolve missing keys in source. Writes land in the dependent and are never propagated down.
  • Shard counts must match between dependent and source; a mismatch is rejected.
  • A dependent is later collapsed with KSPACE MERGE, detached with KSPACE RELEASE, or discarded with KSPACE DROP.
Layering interacts with the ordered fast paths. A space with a source is excluded from the ordered-shard optimizations even when range sharded: keys it answers for may live upstream, and a delete against it leaves a tombstone. Nothing is removed upstream. See Ordered Range Sharding.
Endpoint reference

Commands and constructors

DBSIZE counts stored keys. Redis counts one per key name. Here a hash with twenty fields adds twenty to DBSIZE; Redis would add one. KEYS and SCAN count names. The number comes from counters the shards already keep, because counting names would walk the key space on every call. Use KEYS if you need names.
SELECT does not mean quite what it means in redis. redis has a fixed set of numbered databases - sixteen by default - that share a server and nothing else. barch has named key spaces. Each carries its own shard count, ordering and eviction options, and can depend on another through KSPACE. A number therefore has to be turned into a name, and three differences follow from that.
  • A number becomes a name. SELECT 1 selects the space db1. The prefix is the db_number_prefix option, so CONFIG SET db_number_prefix tenant_ makes SELECT 1 select tenant_1 instead. SELECT 0 is the default space, whatever the prefix.
  • A space named with a bare number cannot be reached through SELECT, because the number is read as a database. Use USE, which only ever takes a name. Setting db_number_prefix to the empty string restores the older behaviour, where SELECT 1 selects a space literally called 1.
  • There is no fixed number of databases. redis refuses SELECT 16 by default; here SELECT 999 brings that space into being like any other. Nothing is allocated until a space is used, so this costs nothing, but a client that expects to be told it has gone out of range will not be.
A name may also be given directly - SELECT events - which redis has no equivalent for. USE does the same thing.

Reference / Coalesced Foreign Sources

Coalesced Foreign Sources

A named space can fill a local miss from MySQL, Postgres, or a Luau script. The caller of GET (or EXISTS, MGET) waits for that fill. Concurrent callers of the same missing key park on one query. The source sees one trip, not a stampede.

L1 · SWIG waitsL2 · RESP parksone query per missing keyshard lock dropped across the network
Design context

What a miss does

Write the foreign options into the configuration space, then open the named space. The space reads those keys once, at first reference, and keeps the source for the life of the process. A later GET that does not find the key locally starts at most one outbound query for that key. The handler drops the shard lock, parks the caller, and returns when the fill lands.

  • One flight per key. The first miss creates a flight and runs the driver. A second GET of the same key finds that flight, parks beside it, and increments foreign_coalesced. It does not open a second MySQL or Postgres session.
  • The client waits. From redis-cli or redis-py the GET does not return until the value is stored, the source miss is cached, the waiter timeout fires, or the driver errors. That is the synchronous load. SWIG KeyValue.get / exists wait the same way.
  • A hit is stored locally. The driver returns one column as the value. The server writes it as an ordinary SET. The next GET is a local hit and does not ask the source again.
  • A source miss is a tomb. The source saying “no such row” is stored as an empty tomb (optional TTL from <name>.missing_ttl). GET, EXISTS, MGET and TTL treat it as absent. The next GET does not query again until the tomb expires or someone DELs it.
  • A driver error is not cached. -ERR FOREIGN … leaves the key missing. The next GET asks again.
This is not PULL. PULL is the unfinished remote-barch path. A foreign source does not subscribe to another barch and does not stream writes. See Replication & Routing.
Set the options before the first USE. A space reads <name>.foreign* when it is built. Changing the DSN or the query after that has no effect until UNLOAD (or a restart) and a new open. Provision every process that will open the space. See Named Key Spaces.
Endpoint reference

Configure a database and a query

Pick a space name. Put a DSN where the configuration space will not replicate a password. Write a query that returns one column. Name the source. Call save() on the configuration handle (RESP SAVE) so the options are on disk. Then open the space.

Query macros

The server never concatenates the key into the SQL string. It rewrites the macros into a prepared statement and binds the values.

MacroWhat is bound or written
?the whole user key (type prefix stripped)
$0, $1, …component n after key_split (a space, if unset). GET Smith 42 binds $0=Smith and $1=42. With catalog.key_split set to :, GET Smith:42 binds the same two
$$the key reconstructed by encoded_key_as_string — the original GET string

Worked example

A space named catalog should answer GET sku from items.v, and GET Smith 42 from a person table qualified by the space name. Write the options, then open the space, then GET. The first GET of each key runs the query. The second is local.

Luau instead of a fixed query

Set <name>.foreign to luau and name a stored function in <name>.foreign_script. Store it with SETF first — the space has to exist before it can hold one, so the order is: configure, USE the space, SETF the script, then let it fill. The script must define call(key, space) and return a string or nil. Nil is a cached miss. A thrown error or a script that runs past the query timeout is -ERR FOREIGN, not a tomb. foreign_script_insns is a slice, not a kill: when it runs out the script pauses and the foreign pool takes other work, then the script continues. sql.query is a blocking C call, so a slice cannot yield in the middle of one. Give the space a DSN as well if call calls sql.query; that call uses the same macros and the same pool. There is no require and no IO.

Caps and timeouts

  • foreign_query_timeout_ms is the driver deadline. A job waits up to that long for a pooled connection, then the statement itself is cut off.
  • foreign_timeout_ms is how long the parked GET waits. It can be longer than the driver deadline. Unset, it inherits the global foreign_timeout_ms (five minutes).
  • foreign_max_inflight is the cap of running queries for the space. A miss above the cap is -ERR FOREIGN overloaded, not a queue that grows without bound.
  • foreign_pool_size is the MySQL or Postgres connection pool for the space. Do not open one connection per query.
  • foreign_pool_max_age_ms is how long an idle pooled connection may sit before the key space maintenance thread closes it. The next miss then opens a new one. Unset, it inherits the global foreign_pool_max_age_ms (thirty seconds). The global 0 keeps idle connections.
  • A stored function called by a client does not use these. Its slice is function_slice_insns and its deadline is function_deadline_ms — see the note below, which is the one thing about them worth reading before you tune either.
The stored-function deadline is wall clock, and it counts queued time.

function_deadline_ms (default one second) runs from the moment a call arrives, not from when it starts executing and not from CPU used. A function only ever runs a slice at a time — function_slice_insns instructions, then it yields its worker so short calls are not stuck behind long ones — and the time it spends waiting for its next slice counts against the deadline just the same.

The consequence is worth stating plainly, because it is a decision rather than an accident: under enough load a function fails rather than being slow. Sixteen scripts started together, each wanting about 0.29s of work, put three of them past a one second deadline. That is the deadline doing its job — it is what bounds a runaway, and a bound that stopped counting whenever the machine was busy would not bound anything. But it means the deadline has to be set against the load you expect and not against how long the function takes on an idle server.

If functions are timing out under load and the work itself is not the problem, raise function_deadline_ms — for the space with <name>.function_deadline_ms if only some of them need it. Lowering function_slice_insns makes each function give up its worker sooner, which helps short calls get through and does nothing for a long one. Read both back with KSPACE OPTION GET FUNCTION_DEADLINE and FUNCTION_SLICE.

A call cut off this way answers an error; nothing it wrote before it was cut is rolled back, since a function is not a transaction.

Stored Luau Functions

User-defined commands written in Luau, stored as ordinary keys in the space they belong to. A function persists, replicates and exports the way any other key does.

SETF · GETF · REMF · KEYSF · CALLFnever evictedfunction ACL category
Design context

What a function is

  • A key, not configuration. A function lives under a lead byte of its own, so it is written to the AOF and RDB, replicates to a peer, and comes out of EXPORT — with no machinery specific to functions. A space's functions have the same lifetime as the space, and FLUSHDB drops them with it.
  • FLUSHALL does not touch configuration. That space holds each space's settings as well as the global functions, so clearing every cache with it would silently unconfigure the server. Every other space is cleared as usual. To clear configuration deliberately, USE configuration and FLUSHDB.
  • Scope. A function is callable in the space it was stored in. Functions in the configuration space are global: defined once, callable from any client in any space, the same scope the barch module itself has.
  • Never evicted. Eviction does not take a function key under any policy. A function is a command, not data — losing one to memory pressure deletes a command, and since a session keeps whatever it compiled, connections that already ran it would carry on working while new ones failed. Defragmentation still moves them.
  • No TTL. EXPIRE and the rest of the TTL family refuse a function. A session holds what it compiled for as long as it is connected, so a TTL would expire the key while every connected client went on calling the function. A setting that visibly does not do what it says is worse than not having one.

The store interface reads the cache; barch.call runs the command. On a space with a foreign source that difference shows: barch.call("GET", k) fills from the source on a miss, exactly as a client's GET would, while barch.store.get(k) answers from what is held locally and never fetches. That is deliberate — filling is something a command does — so a script picks the one it means. Ranges and iteration are local for the same reason, and always have been: no range-shaped command has ever consulted a foreign source either.
barch.tomb is a cached source miss, and it is not the same as nil. A space with a foreign source has three states for a key, not two: the value; barch.tomb, meaning the source was asked and had nothing, and the miss was cached so it will not be asked again; and nil, meaning nothing is there and nobody has asked. A script that folds the last two together cannot tell "does not exist" from "not fetched yet". It is a value with an identity rather than a boolean, so if not v does not quietly collapse the two — say v == barch.tomb when that is what you mean. A tomb whose missing_ttl has lapsed reads as nil again, because the source can be asked once more. On a space with no foreign source nothing is ever tombed, and get only ever answers a value or nil.

Keys are strings, in and out. That is how a key enters and leaves barch everywhere else, so a walk hands back the same text KEYS prints and a script can hand it straight back. A composite key is its components rejoined with the space's split character.

Iterating a space hands back a row that decodes only what is read: row.type (key, list, hash, orderedset, function), row.container, row.key and row.value. It promises what SCAN promises — everything present throughout the walk is seen at least once, repeats are allowed, and a key written or erased after its page was copied may or may not appear. A script that assumes a snapshot will be wrong in a way that is hard to see.

What a script may not do, each refused rather than half-supported: a blocking command such as BLPOP, an asynchronous one such as KEYS, and MULTI/EXEC/WATCH. A transaction belongs to the connection, not to the script.

Design context

Locking, for a read-modify-write

Every read above copies what it needs under the shard lock and drops the lock before a line of Luau runs. That is what keeps script code from ever running while a shard is held, and it means a get followed by a set has a gap another connection can land in. barch.store.locked closes the gap:

barch.store.locked(key, function()
    local n = tonumber(barch.store.get(key)) or 0
    barch.store.set(key, tostring(n + 1))
end)

The lock is a write lock on the shard the key routes to, or on every shard when no key is named. It is scoped rather than a lock and an unlock to pair up: the lock goes back whether the function returns, raises, or is cut off, which a pair cannot promise.

Inside a locked region the rules are narrow, deliberately.
  • One shard, or the whole space — never two. Reaching a second shard aborts the call. Two scripts each holding one shard and waiting for the other is a deadlock nothing recovers from. Use shardNumber to check two keys are together before locking, or put them in one container, which routes them to a single shard by name.
  • No barch.call, which would take shard locks of its own.
  • No sql.query, which would stall every connection on that shard for as long as the remote takes.
  • No yielding. The instruction budget inside the region is a hard cap rather than a slice, and running past it raises. A call that parked holding a shard lock would never come back.
  • No nesting — an inner region is already covered by the outer hold.

So store.range, and a container living elsewhere, are not usable inside a single-key region. Under the whole-space form they are, since every shard is held.

Design context

Time and memory

  • The slice. function_slice_insns instructions, then the call yields its worker and is queued for its next slice, so a short call is never stuck behind a long one. It is not a kill.
  • Nesting. A function reaches another through barch.call("CALLF", …), and each level runs with a deadline of its own — so the depth is capped at function_max_depth (100). A chain past it is refused rather than allowed to recurse until something else gives way. Raise it if a script is meant to recurse deeply.
  • The deadline. function_deadline_ms is wall clock from when the call arrives and keeps counting while the call waits for its next slice. Under enough load a function fails rather than being slow. See the note under Caps and timeouts, which is worth reading before tuning either.
  • Compilation. Each function is compiled once per session and space and kept, so a warm call neither reads the source nor compiles it. A running session does not pick up a redefinition; a new connection does.
  • Sandboxing. The base globals are frozen, and a global one function writes lands in its own table where the next function cannot see it.
Reference / Memory Model

Memory: Structural Prefix Elimination

A hash map stores every key whole, once per entry. A radix trie stores each distinct byte-sequence once, at the depth where it stops being shared. Shared structure is stored once. Put the shared part first; measure the result with HEAPBYTES and STATS.

L1L2 · RESPkeys: shared prefixes stored oncevalues: optional zstd/fsst
Design context

Where the bytes go

The trie

  • Path compression. A run of single-child edges is collapsed into one node carrying a partial prefix (up to 10 bytes inline per node), so a long unbranching stretch of key does not cost one node per byte.
  • Adaptive fan-out. Interior nodes are sized to their actual child count — node4, node16, node48, node256 — instead of allocating a fixed 256-way array, so a sparse branch costs a small node and a dense one costs a fast one.
  • No per-entry key copy. The key is reconstructed from the path walked to reach the leaf. Two keys sharing an n-byte prefix pay for those n bytes once between them, not twice.
  • No per-entry hash bucket. There is no bucket array to keep sparsely occupied and no per-entry hash to store.

Measured: roughly half the footprint of a standard hash map at similar single-threaded latency. The margin widens as keys get longer and more structurally similar.

Key layout

The saving is a function of how much leading structure the keys share. Two schemes holding identical data can differ substantially in resident size:

Key schemeShared structureTrie consequence
tenant:4471:user:00012:profilelong, left-aligned, highly sharedthe whole tenant:4471:user: stretch is stored once for every key beneath it
00012:profile:user:4471:tenantsame bytes, reversed — divergence at byte 0almost nothing shared; each key pays for its own path
a7f3c9e1… (hash/UUID first)none by constructionworst case; branch factor saturates immediately at the root
Put the low-cardinality component leftmost. Order key components from most-shared to least-shared. The same left-aligned structure that shares bytes makes RANGE prefix: prefix:~ a bounded subtree walk.

Patterns that cost less here

  • Prefix namespacing to fake isolation. Prefixing every key with app:v3: to separate tenants or environments costs those bytes in a hash map. Here the prefix is shared. Where the isolation is real, a named key space takes the prefix off the key and gives the space its own shards, options, and persistence.
  • Hash-per-object to amortize key overhead. A common Redis pattern is packing fields into a hash because a hash field is cheaper than a top-level key. Here, flat composite keys (obj:00017:field) already share their prefix, so pick the shape by access pattern. Flat keys stay individually rangeable and TTL-able. The hash API is still the right tool when the whole object is read together or field-level TTL is needed.
  • Client-side key shortening. Abbreviating user_profile: to up: to save memory trades readability for bytes that a trie was going to share anyway. Prefer descriptive, well-ordered keys.
  • Sorted-set-as-index for ordering. Maintaining a parallel Z* index purely to get ordered access duplicates every member. Ordered key spaces give ordering from the primary key itself — see ordered operations.
Value compression does not compress keys. compression zstd|fsst applies to values in the arena. Keys stay raw bytes, so ordering and range complexity stay the same. Measure prefix elimination with bytes_allocated and value compression with value_bytes_compressed.
Random-first keys defeat the mechanism. UUID-, hash-, or timestamp-ms-first keys share no leading structure, saturate the root's fan-out, and give up both the memory saving and the range locality. If an opaque identifier must lead, put a stable low-cardinality component ahead of it (region:eu:, shard:07:). On a range-sharded space, uniformly random leading bytes are the workload the rebalancer handles best; monotonically ascending ones are the workload it handles worst.

AUTH & ACL

Category-based access control on the RESP surface. ACL state is stored apart from cache data and is not replicated.

L2 · RESP only13 permission categoriesnot replicated
Design context

Model

  • Scope: ACL administration is only available on the native RESP interface (default port 14000). Embedded SWIG calls execute in-process and skip AUTH. Isolation is the process boundary.
  • Session model: on connect, the default user is authenticated implicitly; if it has no explicit rights configured, all rights are assumed. AUTH switches to a named user.

Dictionary Compression

Value compression with zstd (dictionary-trained) or fsst, toggled at runtime. Training via TRAIN builds a shared dictionary that compresses all subsequent values.

L1L2 · RESPruntime togglevalues only — keys stay uncompressed
Design context

Engine implications

  • Scope: compression applies to values in the arena; trie keys remain raw bytes, so ordered navigation and range complexity are unaffected.
  • Cost model: writes pay dictionary compression, reads pay decompression — a per-value constant. value_bytes_compressed in STATS measures realized savings against logical_allocated.
  • Dictionary lifecycle: at least five TRAIN "sample" calls accumulate samples; a bare TRAIN finalizes and persists the dictionary. If compression is enabled with no dictionary, barch trains automatically from live values and saves the result.
Dictionary compression pays off on small, repetitive values. JSON fragments, URLs, and codes shrink. Large already-compressed blobs do not.
